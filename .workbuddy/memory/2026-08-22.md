## 语音"后续无声"定位与修复

用户实测反馈：首页选人有语音，但开场/对话回复/结束无声。用 Playwright 注入探针追踪 `speechSynthesis.speak/cancel` + utterance `onstart/onerror` 定位：

**根因**：`speak()` 函数里 `cancel()` 后**同帧立即** `speak()`（时间戳完全相同）——Chrome/Safari 已知竞态：`cancel()` 异步生效会"迟到"，把紧随其后 speak 的新语音误取消。首页 cancel 时队列空故无害（有声），后续 cancel 真实取消正在播的首页语音、误伤新语音（无声）。

**修复**（commit 26f904c）：`speak()` 改为 `cancel()` 后 `setTimeout(120ms)` 再 speak；并给 utterance 加 `onerror` 回退（指定 voice 失败时用默认 voice 重播）。已验证：开场语音 speak + onstart(START) 均触发，speaking=True。

**关键经验**：Web Speech API（SpeechSynthesis）的 `cancel()`+`speak()` 必须隔开一帧，不能同帧；诊断语音问题要在 utterance 上绑 `onstart/onerror` 追踪，不能只看 `speak()` 是否被调用。

## 对话无反应排查（进程冲突）

用户反馈对话无反应。排查：日志里**无 POST /api/chat 记录**，curl 直测 /api/chat 卡死（exit 137）。但 `config.llm` 直测 DeepSeek 秒回 OK——说明**非 LLM 问题**。

**根因**：之前用 `nohup` + `run_in_background` 各启动一个 uvicorn，**两个进程同时监听 8000**，请求被路由到卡住的进程，导致 /api/chat 挂死。

**修复**：`lsof -ti:8000 | xargs kill -9` 清掉全部进程，干净启动单后端。验证：curl /api/chat 200（3.4s 返回正确回复），Playwright 模拟对话 ok，无 JS 错误。

**教训**：启动后端前必须先确认无残留进程（`lsof -ti:8000`），避免端口冲突导致请求挂死；排查"对话无反应"先看日志有无对应请求、再用 curl 直测接口定位是前端还是后端问题。

## ASR 与 TTS 降级定位（用户挂 VPN 后）

用户反馈：挂 VPN 后流程通了（ASR 正常），但语音音色不对，怀疑走降级。看 `logs/app.log` 定位：

1. **ASR 根因确认**：挂 VPN 前 Web Speech API 走 Google 服务被墙导致识别失败（`识别失败(network)`）；挂 VPN 后正常（`chat 请求 text='一二三四五六七'`）。国内部署需接腾讯云/讯飞 ASR。
2. **TTS 降级根因**：日志显示 Edge-TTS **合成成功**（"tts 完成"），但对话回复后**无第二条 TTS 请求**——前端 `_ttsAvailable` 缓存 bug：首页 `audio.play()` 被 Chrome autoplay 拦截（无用户手势），catch 里把 `_ttsAvailable` 永久设 false，导致后续对话不再尝试 Edge-TTS、一直用浏览器机械音。

**修复**（commit 6748e38）：区分「网络失败」（fetch 失败→永久降级）与「播放被拦截」（audio.play 失败→不永久降级，下次有用户手势再试）。对话回复（有用户手势）现会用 Edge-TTS 晓晓音色；首页自动播报仍受 autoplay 限制，后续可加"点一下开始"解锁。

**关键经验**：前端缓存降级状态时，要区分「服务不可用」（可缓存）与「一次性失败如 autoplay 拦截」（不可缓存），否则一次偶然失败会永久劣化体验。
