# 鸭鸭日记本：Figma 全产品交互与 UI 设计迁移规格

- 日期：2026-08-30
- 类型：前向生效的设计交付合同
- 状态：聊天范围已确认，书面规格待用户复核
- 适用产品：幼儿端与教师端全部用户可见界面

## 1. 决策与边界

项目不再等待 Lovable 原型。仓库现有 `docs/lovable/` 只是未实际执行的两页教师端输入包，没有分享链接、截图、组件、令牌或其他视觉资产，因此本次工作不是搬运旧原型，而是以当前代码和已确认交互合同为基线，新建完整的 Figma 设计资产。

本规格前向取代“仅制作教师端今日任务和审阅工作台两个 Lovable 页面”的设计交付要求，但不改写历史事实：

- 旧 Task 9 canonical run 仍是 `TECHNICAL_NO_GO / LOVABLE_DELIVERABLE_MISSING`。
- 旧 `docs/lovable/**`、Task 7–9 记录和生成的验收报告保持历史原样。
- Figma 交付完成后，另立小范围任务更新未来发布门槛；当前不重写 acceptance runner。

## 2. 设计真源

- **Figma**：视觉层级、布局、组件、设计令牌、交互流程和评审批注的设计真源。
- **现有代码**：接口、状态机、可达操作和运行行为的实现真源。
- **浏览器测试**：故障恢复、数据一致性、键盘操作和发布验收的行为真源。
- **代码映射清单**：把 Figma 页面、组件和关键节点映射到现有 HTML、CSS 与 ES module；Figma 不替代运行测试。

## 3. 全产品覆盖范围

### 3.1 幼儿端，第一优先级

幼儿端是一个单页应用，但每个状态都是独立的设计评审表面。Figma 必须覆盖：

1. `welcome`
2. `loading_roster`
3. `selecting_child`
4. `opening`
5. `ready`
6. `listening`
7. `submitting`
8. `speaking`
9. `submission_failed`
10. `saving_conversation`
11. `completed`
12. `recovery`

同时覆盖教师帮助弹窗的锁定、PIN 解锁、补录、保存草稿、重试麦克风、安全结束、再次检查和重新锁定状态。

幼儿端重点不是增加装饰，而是让低龄使用者清楚感知：现在能否说话、系统是否听见、内容是否正在发送、鸭鸭是否正在回复、失败时原话是否保留、何时可以安全结束，以及何时需要老师帮助。

### 3.2 教师端

覆盖教师壳层、首次设置 PIN、解锁、立即锁定、鉴权失败和运行时不可用，并覆盖全部七个业务路由：

1. `today`
2. `children`
3. `ducks`
4. `roster`
5. `review`
6. `growth`
7. `search`

每个路由至少包含默认、加载、空、失败和可恢复状态；适用页面还需覆盖保存中、保存成功、确认完成、修订冲突、脏状态离开提示、停用/恢复和撤销反馈。

## 4. 目标视口与无障碍

- 幼儿端：`1024×576`、`1280×720`。
- 教师端：`1024×768`、`1440×900`。
- 核心触控目标不小于 `44×44px`。
- 普通文字对比不低于 `4.5:1`；UI 边界和焦点指示不低于 `3:1`。
- 键盘焦点、读屏状态、错误恢复和 reduced-motion 方案必须体现在组件与流程注释中。
- 幼儿端优先考虑一眼可懂、单主行动、低文字负担、明确等待和稳定布局。

## 5. Figma 文件结构

采用一个 Figma Design 文件，页面结构固定为：

1. `00 Cover & Handoff`：范围、版本、代码 HEAD、评审状态与使用说明。
2. `01 Foundations`：颜色、字体、字号、间距、圆角、边框、阴影、焦点和动效令牌。
3. `02 Components`：共享按钮、输入、状态提示、卡片、队列行、对话消息、弹窗和导航组件。
4. `10 Child · Core States`：十二个幼儿状态的双视口设计帧。
5. `11 Child · Recovery & Teacher Help`：失败、保稿、老师帮助和安全结束。
6. `12 Child · Prototype Flows`：核心语音循环、失败重试、完成和恢复流程。
7. `20 Teacher · Shell & Auth`：教师壳层、PIN 和运行时状态。
8. `21 Teacher · Today`
9. `22 Teacher · Children`
10. `23 Teacher · Ducks`
11. `24 Teacher · Roster`
12. `25 Teacher · Review`
13. `26 Teacher · Growth`
14. `27 Teacher · Search`
15. `30 Cross-product Flows`：幼儿完成到教师分析/审阅的跨端状态链。
16. `90 Code Mapping & Acceptance`：Figma 节点、代码模块、测试节点和未决项的映射。

## 6. 组件与代码映射

设计系统不引入 React 假设，优先映射当前原生 HTML/CSS/JavaScript：

- 幼儿端壳层和状态：`app/frontend/index.html`、`app/frontend/child/view.mjs`、`machine.mjs`、`styles.css`。
- 教师端壳层和路由：`app/frontend/teacher.html`、`teacher/app.js`、`teacher/router.mjs`。
- 教师业务视图：`teacher/views/today.mjs`、`management.mjs`、`review.mjs`、`reports.mjs`。
- 视觉素材：`app/frontend/assets/`。

Figma 变量名称应尽量保留现有 CSS 语义；不能一一对应的令牌先在 `90 Code Mapping & Acceptance` 标记差异，不提前修改产品 CSS。

## 7. 原型流程

必须可点击演示以下流程：

### 幼儿端

- 欢迎 → 加载值日生 → 选择幼儿 → 开场 → 准备说话。
- 准备说话 → 正在听 → 正在发送 → 鸭鸭回复 → 下一轮。
- 发送失败 → 原话保留 → 重新发送 → 成功回复。
- 保存会话 → 完成 → 换下一位幼儿。
- 麦克风/存储/恢复失败 → 老师帮助 → 安全补录、重试或结束。

### 教师端

- PIN 解锁 → 今日任务 → 分析中/失败/待审阅队列。
- 待审阅 → 查看详情 → 修改 → 保存草稿 → 确认完成。
- 排班、幼儿和小鸭的新增、停用、恢复及失败重试。
- 成长与搜索的加载、空、结果和错误状态。

## 8. 制作顺序

1. 创建 Figma 文件与 Foundations/Components 骨架。
2. 完成幼儿端十二状态、老师帮助和四条核心原型流。
3. 完成教师壳层与七个业务路由。
4. 完成跨端流程与代码映射。
5. 用户进行视觉和交互评审；记录节点级修改意见。
6. 评审通过后，另行制定产品样式落地任务和未来 release gate 更新。

任何阶段都不连接应用数据库、不上传日志、API key 或真实幼儿资料。制作基线使用现有界面、虚构内容和本地页面视觉捕获。

## 9. 交付证据

Figma 设计完成的最小证据为：

- 可访问的 Figma Design 文件 URL 与 file key。
- 上述页面结构和双视口覆盖矩阵。
- 幼儿端与教师端核心 prototype flow 起止节点。
- Foundations 变量、共享组件和代码映射表。
- 用户评审结论、未决项和设计版本时间。

当前 Figma 账户连接已验证，但席位返回 `View`。创建或修改正式文件前必须获得一个具有编辑权限的 Design 文件；可以由用户提供可编辑文件，也可以在席位允许后由工具创建。

## 10. 精简执行原则

- 设计文档、Figma 节点和评审记录属于轻量设计工作，不触发后端、浏览器或完整 acceptance runner。
- 单纯记录设计决定时采用“一人、一处记录、一次范围验证”。
- 产品代码变化才执行定向 TDD；共享状态机、数据或发布边界变化才升级为完整门禁。
- P0/P1 阻塞当前阶段；P2 记录到设计 backlog，不重复触发完整审查。
- 旧 canonical 证据保持不可变，新的设计交付用新的前向证据记录。

## 11. 非目标

- 不把 Figma 生成物直接当作生产代码。
- 不在本阶段修改产品 API、数据库、状态机或现有测试。
- 不全仓替换历史 Lovable 文本。
- 不把旧 Task 9 NO-GO 改写为 GO。
- 不要求移动端完整重构。

## 12. 规格完成条件

用户确认本书面规格后，下一步创建或接入具有编辑权限的 Figma Design 文件，并按第 8 节顺序制作；在该确认之前不创建或修改 Figma 设计资产。
