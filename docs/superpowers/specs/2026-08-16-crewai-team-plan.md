## 1. 背景与目标

鸭鸭日记本需求已收敛（单体 FastAPI + React + SQLite + DeepSeek，含语音、对话引擎、提炼、评估、小鸭档案、成长曲线等）。本项目引入 **CrewAI** 组建一个"AI 研发团队"，以多 Agent 协作方式完成从**交互设计 → UI 设计 → 后端开发 → 前端开发 → 测试 → 验收**的全流程，直至交付**可供验收的产物**（可运行的 Web 应用 + 验收报告）。

## 2. 为什么采用 CrewAI + Graph Engineering

采用 **Flow 作为编排层、Crew 作为执行单元、Agent 作为角色** 的三层架构，核心理由：

1. **流程可审查、可可视化**：用图工程（Flow + `@listen`/`@router`）把整条研发流水线显式化为一张有向图，`flow.plot()` 一键生成交互式拓扑图，团队可直观审查依赖与执行路径，而非黑箱脚本。
2. **职责单一、边界清晰**：每个 Crew 只负责一个阶段（设计/后端/前端/测试/验收），Agent 只扮演一个角色；`allow_delegation=False` 防止角色越界，便于独立测试与替换。
3. **并行缩短周期**：后端与前端靠"API 契约"解耦后**并行开发**，再经 `and_` 汇聚到集成测试，显著压缩总时长。
4. **质量闭环**：`@router` 条件分支 + 回退环，测试/验收不通过自动回到对应开发阶段修复重跑，避免"交付即埋雷"。
5. **关键节点人机回环（HITL）**：设计确认、验收两个节点用 `human_feedback` 保留人工决策权，防止 AI 在方向性与质量验收上失控。
6. **断点续跑与成本可控**：`@persist` 持久化状态（默认 SQLite），长流程中断后可从快照恢复，不必从头重跑；`usage_metrics` 聚合全流程 token 消耗，配合 DeepSeek 按量计费做成本监控。
7. **与现有资产一致**：复用已跑通的 `config/llm.py`（DeepSeek V4 Pro）与 CrewAI 1.15 环境，零额外基础设施。

## 4. 各 Agent 角色定义与职责边界

| Crew | Agent | 角色定义（role/goal/backstory 要点） | 职责边界（只做） |
|---|---|---|---|
| 设计 Crew | 产品经理 | 把需求规格拆为可执行的 PRD 与验收清单 | 产出 PRD + 验收标准；不写代码 |
| 设计 Crew | 交互设计师 | 设计幼儿端/教师端页面流程与对话脚本 | 产出交互稿（页面流转、PTT、对话节奏）；不画视觉 |
| 设计 Crew | UI 设计师 | 定义设计 token、组件规范、视觉稿 | 产出 UI 规范 + 视觉稿（幼儿端亮色投影风 / 教师端专业风）；不写业务代码 |
| 设计 Crew | 系统架构师 | 定技术架构、数据模型、API 契约、目录结构 | 产出架构文档 + API 契约 + DB schema；作为前后端解耦的"合同" |
| 后端 Crew | 后端工程师 | FastAPI + SQLAlchemy + SQLite 实现数据层与 API | 按 API 契约实现接口、数据模型、排班/档案/审阅等业务 |
| 后端 Crew | AI 引擎工程师 | 实现对话引擎、信息提炼、能力评估、小鸭档案汇总 | 编写 LLM 结构化输出（JSON schema）、prompt、上下文注入；不碰前端 |
| 前端 Crew | 前端工程师（幼儿端） | React 实现幼儿端：PTT 语音、动画、投影友好 | 幼儿端页面与交互动画；不碰教师端与后端 |
| 前端 Crew | 前端工程师（教师端） | React 实现教师端：管理、审阅、成长曲线、明细检索 | 教师端页面与图表；不碰幼儿端与后端 |
| 测试 QA Crew | 测试工程师 | 编写并运行单元/集成/端到端测试 | 产出测试用例 + 测试报告；不修改业务代码 |
| 测试 QA Crew | 代码审查员 | 审查代码质量、边界、安全、与契约一致性 | 产出审查意见；不改代码，意见供回退修复消费 |
| 验收 Crew | 验收负责人 | 对照验收清单逐项核验产物是否达标 | 产出验收报告（通过/不通过 + 缺陷清单）；不修改产物 |

**边界纪律**：所有 Agent `allow_delegation=False`；跨阶段的数据只通过"契约产物"（文档/API 契约/代码文件）流转，不直接互相调用。

## 5. Agent 间消息传递与依赖关系（图结构）

**Crew 内部**（顺序）：用 `Task.context` 传递——下游 Task 引用上游 Task 输出（如架构师的 API 契约 → 后端工程师的实现任务）。

**Crew 之间**（图边）：用 Flow 的 `@listen` 依赖 + `self.state` 共享，返回值作为数据流。

依赖图（与编排图一致，此处标注"谁依赖谁、传什么"）：

| 边（上游 → 下游） | 传递内容 |
|---|---|
| 需求规格 → 设计 Crew | 需求规格文档路径 |
| 设计 Crew → 后端 Crew | PRD + API 契约 + DB schema + 验收清单 |
| 设计 Crew → 前端 Crew | PRD + UI 规范 + 视觉稿 + 交互稿（同一份设计产物，**并行**下发） |
| 后端 Crew + 前端 Crew → 测试 QA Crew | 代码产物路径 + API 契约（`and_` 汇聚，两端都完成才触发） |
| 测试 QA Crew → 验收判定 | 测试报告（通过/不通过 + 缺陷清单） |
| 验收判定 → 验收 Crew（通过） | 完整产物 + 测试报告 |
| 验收判定 → 回退修复（不通过） | 缺陷清单 + 定位的失败项 |
| 回退修复 → 后端/前端 Crew | 修复指令（路由回对应阶段重跑） |

## 6. 任务编排方式

| 机制 | 应用点 | 说明 |
|---|---|---|
| 顺序（`@listen` 串行） | 需求 → 设计 → 开发 → 测试 → 验收 | 主干为严格顺序 |
| 并行（多个 `@listen` 同一输出 / `@start` 多分支） | 后端 Crew ∥ 前端 Crew | 设计产物就绪后，两端并行开工 |
| 汇聚（`and_`） | 后端 + 前端 → 测试 QA Crew | 两端全部完成才进入集成测试 |
| 条件分支（`@router`） | 测试通过 / 不通过；验收通过 / 不通过 | 按报告结论路由到"验收"或"回退修复" |
| 回退环（图上的有向回边） | 不通过 → 定位修复 → 回到对应开发 Crew 重跑 | 形成质量闭环，最多重试 N 次（默认 3）后升级人工 |
| 人机回环（`human_feedback`） | 设计确认、验收确认 | 关键节点暂停，等你（主人）批准后继续 |

## 7. 数据在团队间的流转

统一用一份 **Pydantic 状态**（`DeliveryFlowState`）承载跨阶段数据，各 Crew 的产出落盘为文件，状态里只存"路径 + 结构化结论"：

```python
class DeliveryFlowState(BaseModel):
    requirements_doc: str = ""          # 需求规格路径
    design: DesignArtifacts | None = None    # PRD/交互/UI/契约/验收清单
    api_contract: str = ""              # API 契约 + DB schema 路径
    backend_ok: bool = False
    frontend_ok: bool = False
    test_report: TestReport | None = None   # 通过/不通过 + 缺陷清单
    acceptance_report: AcceptanceReport | None = None
    retry_count: int = 0
```

**流转规则**：
- 结构化、需跨阶段消费的数据 → `self.state`（Pydantic，类型安全）。
- 大产物（代码、文档、视觉稿）→ 落盘到约定目录（如 `outputs/design/`、`app/backend/`、`app/frontend/`），状态只存路径。
- 阶段间的"合同"（API 契约）→ `output_pydantic` 强制结构化，前后端据此对齐。
- 全程 `@persist` 持久化状态，支持断点续跑（Resume）与快照分叉（Fork）。

## 8. 各 Agent 的工具集

| 工具 | 用途 | 使用者 |
|---|---|---|
| `FileWriterTool` / `FileReadTool` / `DirectoryReadTool` | 读写产物文件、检索既有代码 | 设计/后端/前端/测试/验收全员 |
| `CodeInterpreterTool`（或本地 Bash 落地） | 运行后端启动检查、pytest、前端 build | 后端/前端/测试 Agent |
| LLM 结构化输出 `output_pydantic` | 强制产出符合 schema 的契约/报告/代码片段 | 架构师、AI 引擎、验收 |

> 落地说明：Agent 产出"代码/文档内容"后，由 Flow 编排方法负责把内容**落盘**并**运行验证命令**（如 `pytest`、`npm run build`），验证结果回写状态作为下一阶段的输入。这样把"LLM 生成"与"可执行验证"解耦，保证产物真实可运行，而非仅停留在文本。

## 9. 验收交付标准

**可验收产物**（最终必须存在且可运行）：

| 产物 | 通过标准 |
|---|---|
| 后端（`app/backend/`） | FastAPI 可启动；数据模型与 API 契约一致；对话/提炼/评估/小鸭档案接口可用；pytest 通过 |
| 前端（`app/frontend/`） | `npm run build` 通过；幼儿端（PTT 语音对话 + 动画 + 投影友好）与教师端（管理/审阅/成长曲线/明细）可运行 |
| 端到端 | 核心流程可跑通：排班 → 幼儿对话（含轮次控制/提前终止/历史感知）→ 提炼 → 评估 → 教师审阅确认 → 成长曲线 |
| 测试报告 | 核心用例全部通过，缺陷清单为空或已闭环 |
| 验收报告 | 对照需求规格逐项勾选，结论为"通过"，含遗留项与风险说明 |

**验收流程**：验收 Crew 产出验收报告 → `@router` 判定 → 通过则交付；不通过则带缺陷清单回退修复，重跑后再次验收（重试上限后升级人工决策）。

## 10. 落地实施建议

- 依赖：`crewai[litellm]>=1.15`（已有）+ 结构化输出所需（Pydantic 内置）。
- 目录结构：
  ```
  pomegranagent/
  ├── config/llm.py                 # 复用现有 DeepSeek LLM
  ├── crews/
  │   ├── design_crew.py            # 设计 Crew
  │   ├── backend_crew.py           # 后端 Crew
  │   ├── frontend_crew.py          # 前端 Crew
  │   ├── qa_crew.py                # 测试 QA Crew
  │   └── acceptance_crew.py        # 验收 Crew
  ├── flows/
  │   └── delivery_flow.py          # Flow 编排 + Pydantic 状态 + @router
  ├── outputs/                      # 各阶段产物落盘目录
  └── main.py                       # 入口：flow.kickoff()
  ```
- 运行：`flow.kickoff()` 启动；`flow.plot("delivery")` 出拓扑图；中断后 `kickoff(inputs={"id": ...})` 续跑。
- 成本：V4 Pro 较贵，建议"设计/架构/验收"用 `deepseek-v4-pro`，"代码生成类"可用更经济的 `deepseek-v4-flash` 分级配置，`usage_metrics` 全程监控。

## 11. 风险与应对

| 风险 | 应对 |
|---|---|
| Agent 产出代码无法直接运行 | 每阶段"落盘 + 运行验证"闭环，不通过即回退重跑，避免文本幻觉 |
| 长流程 LLM 成本高 | 模型分级（pro/flash）+ usage_metrics 监控 + @persist 断点续跑 |
| 并行阶段产物不一致 | API 契约作为唯一"合同"强制结构化，`and_` 汇聚后统一联调 |
| 回退循环失控 | 重试次数上限 + 失败升级人工决策（HITL） |
| 幼儿语音/儿童识别等外部依赖 | 语音供应商可插拔，MVP 用浏览器 Web Speech，不影响开发流水线 |
